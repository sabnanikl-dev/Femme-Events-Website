# Technical SEO verification — PAPI-38 / PAPI-46

This document records the technical SEO baseline for the Femme Events website and the verification posture needed before marking PAPI-38/PAPI-46 fully complete in production.

## Static crawl and share assets

| Asset / route | Expected result | Notes |
|---|---|---|

| `/sitemap.xml` | `200`, XML sitemap content type, includes current self-canonical public routes | Includes `/` only until non-home SPA routes have route-specific canonical metadata. `#services` and `#inquiry-form` are homepage sections, not standalone crawlable routes, so they are intentionally not separate sitemap entries until dedicated routes exist. ## Brand icon set (issue #150)

**Approved source: `public/logo-footer.svg`** — the footer logo ("FEMME" wordmark in brand
brown `#764b36` over the soft pink bloom). Every icon is that artwork, reframed. The wordmark is
never retyped, redrawn, or substituted: `scripts/generate-icons.mjs` nests the original vector
and mask markup unchanged and only changes the viewBox.

- **Crop.** `logo-footer.svg` declares a 252×144 viewBox, but its drawn content occupies exactly
  126×126 units (x 63–189, y 9–135) — the mark is already square, with empty padding around it.
  The generator measures that content box at build time and fails loudly if a future asset is not
  square-safe (aspect outside 0.95–1.05), rather than silently re-composing approved artwork.
- **Canvas.** Icons are flattened onto `--color-femme-cream` `#f7edf0` from the approved palette.
  The source SVG is transparent; an opaque canvas is required because iOS composites
  `apple-touch-icon` over black and a transparent favicon loses the dark wordmark on dark browser
  chrome. No new colours were introduced.
- **Container.** `favicon.ico` is assembled in-script from plain buffers (ICONDIR + ICONDIRENTRY +
  PNG-compressed frames) at 16/32/48/64/128. No icon library was added; the only dependency is the
  existing `@resvg/resvg-js`.
- **No SVG favicon.** `index.html` no longer declares `<link rel="icon" type="image/svg+xml">`.
  Browsers prefer an SVG icon over every raster size, so a competing `/logo-nav.svg` icon would
  shadow the `.ico` that search crawlers fetch. `logo-nav.svg` remains the navbar asset and the
  OG image source — unchanged.
- **Manifest icons are `purpose: "any"`, not `maskable`.** The wordmark spans ~78% of the square,
  which a maskable safe zone (inner 80% circle) would clip. Adding a maskable variant would mean
  re-cropping the approved mark, so it is deliberately deferred.

### Small-size legibility — known physical limit

The mark is a five-letter wordmark spanning ~78% of the icon square. At 16×16 that leaves ~2.5
device pixels per letter, so the letterforms **cannot** resolve — the 16px frame reads as the
brand's pink bloom with a dark wordmark bar. This is a raster limit, not a generation defect, and
it applies to any faithful rendering of this wordmark. It was verified by rendering the shipped
files at native size and inspecting them at 4× nearest-neighbour:

| Frame | Result |
|---|---|
| 16px | Bloom + dark wordmark bar; individual letters not readable. |
| 32px | Wordmark silhouette legible; letters still not crisply separable. |
| 48px | "FEMME" readable. This is the size Google's favicon crawler uses. |
| 64px+ | Fully crisp. |

We deliberately did **not** invent a simplified monogram or alternate mark to win the 16px case;
the approved asset is preserved at every size. If a small-size monogram is ever wanted, it needs a
brand decision from Karan/Amanda and its own issue.

### Regeneration

```bash
npm run icons     # rewrites the icon set from public/logo-footer.svg
npm run verify:seo
```

Regeneration is deterministic — running `npm run icons` twice produces byte-identical files, so a
regeneration never shows up as spurious diff noise.

## Structured data guardrails

The homepage JSON-LD is limited to `LocalBusiness` + `EventPlanningService` because those business facts are visible or already used on the site. It uses one stable business identity: `https://femmeevents.com/#organization`.

Do not add these until the page has matching visible content and/or approved source data:

- `FAQPage` schema — visible FAQ copy exists, but schema publication should wait for a dedicated copy review so answers are exactly approved.
- `BreadcrumbList` schema — no visible breadcrumb UI exists on the current routes.
- Non-home route sitemap entries — defer `/about`, `/what-happens-next`, and `/journal` until they emit route-specific canonical metadata instead of the homepage canonical URL.
- Review/rating/award claims — no approved visible evidence is present.
- Public directory, GBP, or Search Console actions — out of repo scope and require explicit approval.

## Analytics and conversion posture

Analytics remains provider-agnostic and privacy-conscious (`docs/analytics.md`). Conversion events currently tracked without visitor-entered PII:

- `cta_inquiry_click` for inquiry CTAs, with safe `location` and optional package category.
- `nav_inquiry_click` for navigation inquiry links.
- `inquiry_submit` after successful form submission, with `location` and selected package category only.
- `email_click`, `phone_click`, and `instagram_click` for contact/social clicks.
- `vendor_link_click` with safe vendor/link metadata.

Recommended UTM convention for campaigns:

```text
utm_source=<platform-or-partner>
utm_medium=<organic_social|paid_social|email|vendor_referral|qr|directory>
utm_campaign=<yyyy-mm-short-campaign-name>
utm_content=<creative-or-placement>
```

Keep UTM values lowercase, hyphenated, and non-personal. Do not put names, emails, phone numbers, event dates, venues, or inquiry details in UTM values.

## Post-deploy verification checklist

Run after the PR is merged and Vercel deploys production:

```bash
curl -I https://femmeevents.com/robots.txt
curl -I https://femmeevents.com/sitemap.xml
curl -I https://femmeevents.com/og-image.png
curl -I https://femmeevents.com/about
curl -I https://femmeevents.com/what-happens-next
curl -I https://femmeevents.com/journal
curl -I https://femmeevents.com/favicon.ico
curl -I https://femmeevents.com/favicon-16x16.png
curl -I https://femmeevents.com/favicon-32x32.png
curl -I https://femmeevents.com/favicon-48x48.png
curl -I https://femmeevents.com/apple-touch-icon.png
curl -I https://femmeevents.com/android-chrome-192x192.png
curl -I https://femmeevents.com/android-chrome-512x512.png
curl -I https://femmeevents.com/site.webmanifest
```

Every icon URL must return an image/icon content type. If any returns `text/html`, the SPA
rewrite is shadowing the static file and the icon work is not actually live.

Then open the production site in a browser and verify:

- No browser-console runtime errors on homepage and direct routes.
- The JSON-LD parses as valid JSON and contains no masked contact values.
- The OG image resolves as `image/png` and displays in a link-preview debugger.
- No unsupported claims, reviews, awards, or unapproved service/category assertions were added.
- The browser tab shows the Femme mark (hard-refresh; browsers cache favicons aggressively).
- Google Rich Results Test / Schema.org validator parse the page and do not flag the `logo` field.
- Optional manual spot-check: add the site to an iOS home screen and confirm the Apple touch icon.

Google chooses what it shows in search results. A correct, crawlable icon set and a valid
structured-data `logo` are the inputs we control; they do not force a SERP icon, and any refresh
happens on Google's recrawl schedule.
